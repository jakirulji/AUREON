AUREON — GOOGLE DRIVE OAUTH SETUP & SECURITY GUIDE
===================================================

STATUS
------
This is the one-time AUREON application-owner setup guide. Google Drive OAuth
authorization, callback handling, token exchange/refresh and personal-Worker
credential sync are NOT connected in the current app build yet. Do not treat
these instructions as proof that Connect Google Drive is already working.

ARCHITECTURE — WHICH CLOUD PROJECT DOES WHAT?
---------------------------------------------
1. AUREON's Google Cloud project owns the Google Drive API enablement,
   OAuth consent screen, app verification and Android/Windows OAuth client
   registrations. This is one AUREON application configuration.
2. Each AUREON user owns a separate Firebase project and Cloudflare
   Worker/D1 backend. The user's personal Worker is the destination for that
   user's encrypted provider credential vault and metadata.
3. The central backend-recovery directory (when implemented) is only for
   locating the user's personal backend. It must never store provider tokens,
   passwords, file contents or vault plaintext.
4. Users must never enter Google passwords, OTPs, backup codes or session
   cookies into AUREON. Google login and consent happen on Google's own page.

ONE-TIME AUREON APP OWNER SETUP
-------------------------------
1. Open https://console.cloud.google.com/ using the Google account that owns
   AUREON's application project.
2. Select the AUREON Google Cloud project. Do not ask each end user to create
   a separate Google Cloud project for Drive linking.
3. Open APIs & Services > Library. Search for Google Drive API and enable it.
4. Open Google Auth Platform > Branding. Configure the AUREON app name,
   support email, app logo, developer contact email, homepage, privacy policy
   and terms of service. Use domains owned and verifiable by the app owner.
5. Open Google Auth Platform > Audience. Choose External for a public consumer
   app. During development, add only approved test-user email addresses.
6. Open Google Auth Platform > Data Access. Declare only the scopes that the
   released feature actually uses. The initial product proposal is:
     https://www.googleapis.com/auth/drive.readonly
     https://www.googleapis.com/auth/drive.file
   drive.readonly enables reading the existing Drive library; drive.file alone
   is limited to files created/opened/shared with the app and does not provide
   a full existing-Drive listing. If AUREON later edits arbitrary pre-existing
   Drive files/folders, the broader drive scope may be required. Do not request
   it until the feature and review path are approved.
7. Open Google Auth Platform > Clients and create platform-specific clients:
   - Android: select Android, enter the exact AUREON Android package name and
     the SHA-1 signing certificate fingerprint for the release signing key.
   - Windows: select Desktop app. Desktop native clients are public clients;
     use Authorization Code + PKCE. Never treat a desktop client secret as a
     confidential server secret.
8. Save the generated client IDs in the AUREON project’s approved secure
   configuration/release process. A client ID is not a password. Never commit
   private signing keys, refresh tokens or any real client secret to Git.
9. Test the consent flow with a dedicated test Google account. Confirm granted
   scopes, account subject, cancellation, denied consent, expired access token,
   refresh-token rotation and revoked-consent behavior.
10. Before public release, complete Google's applicable OAuth verification.
    Sensitive/restricted Drive scopes can require verification; restricted
    scope data stored/transmitted by a server may trigger an independent
    security-assessment requirement. Confirm the current Google policy before
    production submission.

RUNTIME FLOW — WHAT A USER WILL DO IN AUREON
--------------------------------------------
1. The user signs into their AUREON Master Account.
2. The user opens Cloud > Add provider > Google Drive.
3. AUREON opens the system browser / supported Google authorization UI.
4. The user selects a Google account and reviews the requested permissions.
5. Google returns an authorization response to the registered native-app
   callback. AUREON validates state and PKCE before accepting the result.
6. AUREON identifies the provider account using Google's stable account
   subject/identity, not display-name matching.
7. The resulting refresh credential is encrypted and synchronized only to
   that signed-in user's own Cloudflare Worker/D1 backend. It must not be sent
   to a shared AUREON token database or another user's Worker.
8. Short-lived access tokens are used only for provider API operations and
   should remain in memory as much as possible. Refresh must handle rotation,
   invalid_grant, revocation and provider throttling.
9. If authorization is cancelled or expires, AUREON marks the provider as
   requiring reauthorization. It must not delete local originals or queued
   uploads.

IMPORTANT: THE PERSONAL WORKER IS NOT THE GOOGLE OAUTH CLIENT
-------------------------------------------------------------
The personal Worker stores that user's encrypted provider credential record
and supports that user's vault restore. It is not where the user creates a
Google OAuth consent screen or a new Google client ID. The callback/token
exchange design must be implemented and security-reviewed before asking users
to connect accounts. The exact callback transport must be fixed in code and
must not accept an arbitrary callback URL supplied by a user.

WHAT USERS MUST NEVER DO
------------------------
- Never paste a Google password, OTP, backup code or session cookie into AUREON.
- Never send refresh tokens, OAuth client secrets, Firebase service-account
  JSON, Cloudflare API tokens, Worker root secrets or recovery keys in chat.
- Never deploy a sample/Hello World Worker and assume it implements OAuth.
- Never enable auto-upload by default or delete provider originals after upload.
